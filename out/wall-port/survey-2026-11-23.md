# Porting "the wall" to glyph3d-rs: survey and proposed plan (2026-11-23)

Written by the lead session (Claude) after a first read of both repos. It is a first
pass: one person's reading, a few hours deep. Every claim below names where it came
from so it can be checked. Section 8 lists what was NOT examined.

## 1. The ask (Ivan, verbatim in substance)

Port `the wall` from the JS app to the RS app and make it the default. The JS app is
usable now; he wants to move off the browser as the main test bed and stop dealing with
a JavaScript main-thread render loop. First step: dig into the latest changes and see
what is there and how it landed. A couple of performance changes are landing in JS now
that are "kinda-sorta specific to the web"; bring them to RS only if it makes sense.
He expects "totally different performance characteristics" natively.

He then said the work will likely run in a long unattended "goal" mode until the whole
thing is implemented, so the plan has to be executable end to end.

## 3. What the wall is, in code terms

- `wall/`: 46 files, 14,146 lines. An infinite orthographic canvas of terminals drawn
  with three.js through `packages/glyph3d-core`. Features: pan/zoom, spawn, move,
  resize, hide/close, lasso, groups (tile, freeform, split panes), fullscreen, snap to
  a drafting-paper grid, text selection and copy/paste, mouse reporting, scrollback,
  title bars and map labels, sidebar, palette, status window, settings and help panels,
  right-click menu, gomuxai agent attach, Agent View (a live transcript beside a
  terminal). Every action is a `wall.*` verb (`wall/wallCommands.js`).
- By dependency class (a subagent read every file's imports): about 4.5k lines pure
  logic (`wallLayout`, `splitTree`, `wallSnap`, `wallKeymap`, `contextMenu`,
  `terminalScroll`, `wallAgentView`, `wallSettings`, `wallConfig`, `chord`,
  `labelPlacement`, `dockLayout`, `WallMouse`, most of `WallStore`/`wallCommands`),
  about 4.6k React/DOM (panels, palette, menus, overlays, Agent View cards, bar
  buttons, lasso and selection outlines, map labels, hold ring, fullscreen veil), about
  0.5k three.js scene (`TitleBar`, `GroupFrame`, `WallPaper`), about 4.4k mixed
  (`TerminalWall`, `WallAgentViews`, `WallFullscreen`, `WallGroups`, `WallCamera`).
- 17 headless `tools/wall-*.test.mjs` files (bun:test) cover the pure logic; they are
  the natural spec for a Rust rewrite. `tools/wall-e2e.mjs` (1,537 lines) and
  `wall-cells-check.mjs` need a browser.
- Core terminal path (not wall code): `collections/TerminalGrid.js` (1,809),
  `TerminalEmulator.js` (464, wraps xterm.js), `InstancedField.js` (1,368),
  `core/glyphMaterial.js` (750), `shaping/cellSprites.js` (480), `FontChain.js` (915),
  `LiveSlugAtlas.js` (524), `collections/terminalSelection.js`, `core/cellAttrs.js`,
  `core/cellClusters.js`.
- Persistence: `WallStore.js`, 13 `localStorage` keys per relay port (positions, names,
  attached, hidden, groups, sidebar, status, config, settings, help, fullscreen,
  fullscreenText, agentViews), pruned against live terminals on connect.

## 4. Terminals: what already exists natively

- `g3d-termd` (JS repo `crates/`, Rust, 22.7k lines across `g3d-termd`, `g3d-hold`,
  `g3d-wire`, `g3d`, `g3d-vendor`): owns each terminal's PTY, process tree and a
  libghostty-vt emulator; holder/brain split; survives restarts. Installed on this Mac
  (`~/.local/bin/g3d`, `g3d-termd`), and a daemon is serving namespaces `wall` and
  `agents` right now (`/tmp/g3d-501/termd-*.sock`).
- Protocol 1.5 (`docs/termd/PROTOCOL.md`): Unix socket, 12-byte framed, JSON control
  frames, raw data frames. `subscribe` with `mode: "raw"` gives one `REPAINT` (VT bytes
  that redraw the screen) then `OUTPUT` (the PTY's bytes unchanged). Roles: `watch`,
  `attach`, `own` (the one owner sets the size). `view` scrolls a subscriber's own view
  into scrollback (arrives as a repaint). `key`, `paste`, `mouse` ops let a client with
  no terminal of its own send events that termd encodes for the program's live modes.
  `status_follow` pushes one status document. Frame type `0x86 CELLS` and
  `mode: "cells"` are RESERVED for packed cells ("S3"), not built.
- `g3d-wire` depends on serde only; `g3d`'s lib half is a blocking client
  (`client.rs`: connect, handshake, request, input; `start.rs`: connect_or_start;
  `paths.rs`). Workspace needs rustc 1.96, edition 2024; this Mac has rustc 1.98.
- In JS the browser reaches termd through a Go relay (`cli/`, 18.5k lines) that forks
  an adapter per terminal and re-frames output as WebSocket `0x01` frames; xterm.js in
  the page parses them. A native client can skip all of that.

## 5. What glyph3d-rs has, and lacks

Has:
- The engine (`native/`, `crates/`): HyperLayout, the Derived glyph field (20-byte
  `DerivedSlot`: x, row, glyph id + wrap segment, colour, item + group), group rows via
  a scene graph (`crates/glyph-scene-graph`), in-place slot writes
  (`GlyphField::write_color`, `write_placements`, `write_colors`...), picking, far-LOD.
  A frame is CPU-prepared `FrameData` with no wgpu type.
- The makepad host (`makepad/src`, 5.7k lines): viewport widget, six draw passes ported
  to makepad shaders (`g3_passes.rs`; instance lanes can be `u32`; glyph blocks are
  retained publications), four panels (HUD, Debug, carrel transport, sessions browser),
  a UI model/adapter split, a definition-engine view built by `build_text_scene`
  (a changed text rebuilds the whole small scene).
- Agent sessions through gomuxai's `agent` CLI (`native/src/agent_transcript/`).

Lacks (each is a gap the port must fill):
1. **No emulator in the client.** Nothing parses VT bytes.
2. **No live cell grid.** The field is laid out at load; there is no per-cell fill
   (background) pass, no style byte (dim, strike, overline, underline styles), no
   underline colour, no cursor, no selection drawing, no ring of rows for scroll.
3. **The atlas is prebaked from the old chain** (`assets/atlas/*.bin`, exported by
   `tools/export-atlas.mjs` from the pinned snapshot `tools/vendor/ref`: Cousine →
   MesloLGS NF Mono → DejaVu Sans, regular only). No Monaspace Neon (the wall's
   default), no bold/italic/bold-italic faces, no box/block/braille/powerline sprites
   generated to the cell, no clusters with combining marks, no live glyph growth.
   Glyph ids are u16.
4. **No orthographic camera** (`CameraMode`: Front, Orbit, Fly).
5. **No wall logic**: layout, groups, splits, snap, fullscreen, z-order, focus.
6. **No wall UI**: none of the panels, menus, palette, overlays.
7. **A four-op command applier** (`native/src/cli/ops.rs`: Pick, Verb, CamPose,
   Highlight) where the wall has a verb router reachable from buttons, chords, menus
   and a CLI. An egui command bus exists only as archive tags (`archive/egui-*`).
8. **No persistence** for a wall's state.

## 6. Performance: what differs natively, and the JS changes in flight

- JS measured (2026-11-12, before termd): a flood is bounded by xterm's parser on the
  main thread (99% of it); the text path itself was cut to 0.02–0.05 ms per update and
  1–10 KB uploaded. Natively each terminal can parse on its own thread, and a whole
  120×40 terminal at 20 bytes a cell is under 100 KB, so even whole-grid re-uploads
  are cheap.
- Uncommitted in JS now: render on demand (`frameloop="demand"`, a `renderLoop` knob,
  `requestFrame` threaded through `SceneSystems`, `SceneTransforms`,
  `TerminalScreenQueue`, `TextureUploads`, plus page input wake events) and MSAA off
  (`antialias: false`; measured 9.7 → 5.8 ms GPU per frame on the M2 at 3024×1964).
  Render on demand is worth carrying over: the makepad viewport advances the scene on
  every next-frame event today (`makepad/src/viewport.rs` header). MSAA: not checked
  whether the makepad pass multisamples.

## 7. Proposed plan

### Decisions (each needs Ivan's answer; my recommendation first)

1. **Client emulator.**
   (a) RECOMMENDED: makepad's `apps/terminal/src/term` — a pure-Rust port of Ghostty's
   terminal subsystem (parser, osc, sgr, modes, page, screen, terminal, stream; about
   9k lines; "no Makepad, no PTY, no I/O"), in the fork the host already builds
   against. Put it behind a narrow seam: bytes in, dirty cell rows out.
   (b) libghostty-vt, as termd uses: identical screen by construction, but brings a Zig
   build and verified source tarballs into this repo's build and into relax's JIT.
   (c) Build termd's packed cells (S3): no client emulator at all, and the browser
   wants it too; but it is new protocol design in the JS repo. Proposed as the later
   swap behind the same seam.
   NOT VERIFIED: that makepad's core reproduces termd's REPAINT faithfully. termd has
   a fidelity gate (29 conformance snippets, `tools/termd-fidelity-check.mjs`).

2. **Who draws the cells.**
   RECOMMENDED: the glyph3d engine — a new cell-grid field mode beside Derived
   (`GlyphFieldMode` is the declared seam), where a cell's position comes from its
   index in the grid (no x/row lanes), each cell carrying glyph, face/style bits,
   foreground, background; drawn by a new makepad pass (fill, then ink, then lines and
   cursor), with a row-ring offset per grid for scroll.
   Alternative: makepad's own terminal widget (`apps/terminal/src/widget.rs`, 2,267
   lines: bg runs, glyph batch, box-drawing shader, cursor) drawing with makepad's text
   renderer. Faster to stand up; gives up Slug coverage at any zoom, the greek and
   far-LOD tiers, and one renderer for code and terminals.

3. **Landing bar for wall pixels.** The makepad host is outside every gate; pixel-ab
   renders through wgpu. Either the wall gets a wgpu twin of the cell pass (so pixel-ab
   can hold it), or its pixels are ungated at first and the engine half (grid model,
   emulator seam, layout logic) is held by cargo-test. RECOMMENDED: the second to
   start, with makepad's remote snapshot (`makepad-remote app <pid> snap`) as a manual
   instrument.

4. **"Default."** Read as: `glyph3d-makepad` with no arguments opens the wall (today it
   needs the engine's CLI, and the native binary with no arguments opens a TUI
   launcher).

### Order of work

1. One terminal on screen: termd client (`g3d-wire`, `g3d` as dependencies, own termd
   namespace), the emulator seam, the cell grid, fills and cursor, keys through termd's
   `key` op.
2. The canvas: orthographic camera, pan/zoom, many terminals, spawn/close/move/resize
   (as owner), title bars, focus and z-order, grid paper, persistence to a file.
3. Text fidelity: a new atlas bake (Monaspace Neon and Argon, four faces each, cell
   sprites), style lines, selection and copy/paste, mouse reporting, scrollback (`view`).
4. Groups, tiles, splits, fullscreen, snap.
5. Panels (sidebar, palette, status, settings, help, context menu) and the `wall.*`
   verbs, reachable from a CLI.
6. gomuxai attach and Agent View; then flip the default.

Render on demand from the start.

### Cautions

- A JS wall is live in termd namespace `wall` on this Mac. A second owner would demote
  its adapters, and the relay re-adopts a terminal whose ownership went vacant. The RS
  client uses its own namespace, or subscribes as `watch`.
- The JS repo is live work with uncommitted edits. Nothing in it is to be changed by
  this port without Ivan's say (the S3 option would change it).
- `AGENTS.md` in the RS repo still calls the JS repo retired, read-only history. Stale.

## 8. What this survey did NOT examine (known thin spots)

- `TerminalGrid.js` and `TerminalEmulator.js` internals: the ring of rows, scroll
  detection, the diff, cursor drawing, `cellAt`, how the border and panel are drawn.
- The glyph shader's cell paths (`glyphMaterial.js`): fill pass, style byte, line
  bands, sprite mode 3, the greek tier, colour handling.
- The font path: `FontChain`, `LiveSlugAtlas`, `slugData`, `cellSprites`,
  `fonts/families.js`; and whether `tools/export-atlas.mjs` in RS can bake the new
  chain (variable fonts, non-zero winding, faces, sprites, composites) or what that
  takes. Whether u16 glyph ids are enough.
- `docs/termd/DESIGN.md` beyond its first 75 lines (2,378 lines), `MACOS.md`, the rest
  of `PROTOCOL.md` (key, paste, mouse, status, flow control, restarts, minimal client).
- makepad's `apps/terminal`: its fidelity, its dependencies (ai-services, wm-api,
  app-registry...), whether `term` can be used alone, its licence terms; makepad's
  `apps/wm` (a canvas of app tiles) and `libs/terminal_core`; whether upstream makepad
  has moved since the fork's tip (2026-11-01).
- The makepad host's limits: partial updates of a retained publication, per-frame
  instance streams, MSAA, text input and IME, clipboard, key event detail (physical
  key, modifiers, repeat) as termd's `key` op needs it, pointer capture, DPI.
- The RS scene model for many independently posed, created and destroyed objects
  (group rows, scene-graph nodes, the item table) and whether a scene can grow.
- Agent View's data path (`agentSessions/*`, `agentEvents/*` relay RPC) versus what
  `native/src/agent_transcript` reads; whether a live follow exists in RS.
- The archived egui command bus, console and palette (`archive/egui-interface-*` tags,
  `out/history/ARCHIVED-BRANCHES.md`) and what of it is reusable.
- workstation (the Linux host) did not answer ssh, so unpushed RS or makepad work there
  was not checked.
- Sizing in time. None was attempted.

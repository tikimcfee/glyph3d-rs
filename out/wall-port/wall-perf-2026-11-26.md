# Native Terminal Wall Performance: Before vs After `term-session` & `WakeGate` (2026-11-26)

End-to-end window-thread, GPU upload, wake-rate, camera pan/zoom, full-screen TUI, mixed-flood, and idle measurements for `glyph3d-native --wall` on `laptop-2` (Apple M2, Metal backend `metal-apple`, `3200×2000` physical `Bgra8UnormSrgb` viewport at `scale_factor = 2.0`, `release` profile).

- **Harness**: [wall-perf.sh](file:///Users/lugo/localdev/glyph3d-rs/.claude/worktrees/wall-e3/tools/wall-perf.sh) + [termd_bench_ctl.rs](file:///Users/lugo/localdev/glyph3d-rs/.claude/worktrees/wall-e3/crates/termd-client/examples/termd_bench_ctl.rs) + [perf.rs](file:///Users/lugo/localdev/glyph3d-rs/.claude/worktrees/wall-e3/native/src/wall/perf.rs) (`GLYPH_WALL_PERF=1` and live `wallctl app.perf [reset]`; merged with `wall` through `b97620b`).
- **Scratch-daemon isolation**: Every run uses a private `0700` `G3D_TERMD_DIR=/tmp/g3d-wp-<pid>/...`, per-PID namespace `wp-<pid>` (refusing `wall`, `agents`, `default`, `rs-wall`, and `probe`), `g3d-termd --idle-exit 5 --env-source daemon`, a per-terminal supervisor enforcing both wall-clock `--ttl-secs` (`SIGKILL` to the child process group) and `RLIMIT_CPU = 15s`, and explicit PID-only teardown verified with `kill -0` before removing any scratch directory.
- **Host load caveat**: `laptop-2` (8 cores: 4P + 4E) carried heavy sibling agent compilation load throughout the day (`vm.loadavg` `15–30` during the Before run, `42–62` during the intermediate `term-session` wake diagnostic run, and `21.4–24.1` 1-min / `37–40` 5-min during the final After run). Where host CPU oversubscription (`>2.5×` core count) inflates `Proc CPU`, tail `draw_ms`, or multi-PTY throughput (`N = 14`), that distortion is explicitly noted below.

## 1. Summary of Changes & Architectural Findings

1. **Pump live-lock eliminated (`4,225 ms` stall → `0.006–0.032 ms` p50, `< 0.1%` of wall time)**:
   - **Before (`3be4c94`)**: `Vt::feed` ran synchronously on the window thread inside an unbounded `while let Ok(ev) = rx.try_recv()` loop. Six of nine flood cases (`yes` `N = 1, 4, 14`, `seq` `N = 14`, `cat-src` `N = 4, 14`) wedged `App::pump` for the entire `4,000 ms` cap after drawing `1` frame (`0.23 FPS`).
   - **After (`crates/term-session` + `WakeGate`)**: All 12 benchmark cases complete every target frame (`stalled = 0`). `App::pump` p50 is **`6–32 µs`** across `1` to `14` flooding terminals.
2. **Wake storm was real for multi-terminal floods (`256 wakes/s` at `N = 14`, up to `40.5 wakes/frame`) — fixed in the window (`native/src/wall/app.rs` `WakeGate`)**:
   - **Where wakes came from**:
     - `termd-client`'s socket reader was **already silent** (`SessionHub::open_with` passes `Box::new(|| {})` to `Termd::connect_or_start_with`).
     - `term-session`'s per-terminal `Coalescer` (`16 ms`, `62.5 Hz`) bounds a *single* terminal cleanly (`~28–40 wakes/s` for `N = 1`, and `0.3–3.0 wakes/s` for `yes` because `Vt::fill` suppresses publishes when scrolled rows are cell-identical `"y"`).
     - Across `N = 14` independent session worker threads with unaligned `16 ms` clocks (`14 × 62.5 Hz = up to 875 Hz`), every `publish_snapshot` called `proxy.send_event(Wake)` unconditionally. While the window waited on 60 Hz VSync or drew a frame, `10–40` duplicate `Wake` events queued in winit's `EventLoopProxy`; measured before `WakeGate` (`0d14474` merge, load `42–62`), `seq N=14` delivered **`1,064 wakes` (`255.7/s`, `10.0 wakes/frame`)** and `cat-src N=14` delivered **`973 wakes` (`228.3/s`, `40.5 wakes/frame`)**.
   - **Where the fix belongs — the window (`native/src/wall/app.rs`, `WakeGate`)**:
     - Only `app.rs` owns `EventLoopProxy<Wake>` (shared by `wall_control::Server` and `Sessions`) and knows both when an unconsumed `Wake` is already queued (`pending: AtomicBool`) and when `window.request_redraw()` is already armed for the next surface frame (`redraw_armed: AtomicBool`).
     - `control_wake` deduplicates `pending` (keeping `wallctl` latency `< 0.1 ms` regardless of VSync), while `session_wake` skips `send_event(Wake)` whenever `redraw_armed || pending`, and `App::draw` calls `self.pump(false)` after clearing `redraw_armed` so all 14 terminals' freshest snapshots are swept once right before building each frame. Zero changes were needed in `crates/term-session` or `crates/termd-client`.
     - **Effect**: `N = 14` wakes dropped from **`1,064w` (`255.7/s`) → `110w` (`33.7/s`)** on `seq` (`7.6×` fewer) and **`973w` (`228.3/s`) → `101w` (`24.1/s`)** on `cat-src` (`9.5×` fewer, `< 1 wake/frame`).
3. **Covered-window redraw spin fixed (`native/src/wall/app.rs`)**:
   - On macOS, calling `window.request_redraw()` while `get_current_texture()` returns `Cst::Occluded` fires `RedrawRequested` immediately on the next `CFRunLoop` turn (`~0.1 ms`), bypassing `ControlFlow::WaitUntil(16ms)` and spinning at `~8–10 kHz` (and leaving `--frames N` stuck at `frames == 0`).
   - `App` now tracks `occluded` (`WindowEvent::Occluded` + `Cst::Occluded | Timeout` vs `Success | Suboptimal`) and throttles covered counted runs and animations to `COVERED_TICK = 32 ms` (`~31 Hz`) via `ControlFlow::WaitUntil` + `draw(false)`.
4. **Naming the `582 ms` worst frame (`WorstFrame` sub-stage attribution)**:
   - The inline probe previously in `app.rs` timed `now.elapsed()` across all of `App::draw(true)`, lumping **`g.surface.get_current_texture()` (`[CAMetalLayer nextDrawable]`)** and **`queue.submit` + `queue.present`** into `draw_ms`.
   - `WallPerf` now splits every frame into `pump`, `acq` (`get_current_texture()` swapchain/WindowServer wait), `render` (CPU `wall.tick` + `describe_frame_chrome` + `WallRenderer::render` + `egui`), and `submit` (`queue.submit` + `queue.present`), and records the exact breakdown of the single worst end-to-end frame (`worst_ms=total,idx,acq,render,submit,pump,rows`).
   - **Verdict on `mixed-8yes-1cat-1quiet` (`8 yes + 1 cat-src + 1 quiet focused`)**: Confirmed **`50.89 FPS`** (`240 frames` in `4.72 s`), **`pump` = `3.88 ms` total (`0.082%` of wall time, max `0.070 ms`)**, and worst frame **`98.487 ms` at frame `#4`: `acq = 95.888 ms` (`97.4%`), `render = 0.695 ms`, `submit = 1.893 ms`, `pump = 0.011 ms`**.
   - **Name of the `582 ms` spike**: **macOS `CAMetalLayer::nextDrawable` (`wgpu::Surface::get_current_texture`) swapchain/WindowServer backpressure** (up to QuartzCore's 1 s drawable timeout during window mapping, Space/compositor contention, or load spikes — plus frame-`#0` Metal command-buffer/pipeline warmup `submit` on 14-terminal cold start, `102.1 ms` on `cat-src N=14`). It is **not** terminal pumping (`<= 0.07 ms`) and in steady `N <= 10` runs **not** CPU rendering (`p50 = 0.6–1.4 ms`).

## 4. Limiter Analysis (With Evidence per Case)

1. **`N = 1..4` floods (`yes`, `seq`, `cat-src`), `fullscreen-tui` (`N = 1`), `wheel-pan-zoom` (`N = 14`), and `mixed-8yes-1cat-1quiet` (`N = 10`) → Limited by 60 Hz Display VSync (`PresentMode::Fifo`)**:
   - **Evidence**: `Wait p50` inside `g.surface.get_current_texture()` is **`14.95–15.96 ms`** (`1 / 60 Hz = 16.67 ms`), while window-thread CPU `Pump p50` is **`0.006–0.024 ms`** and CPU `Draw p50` is **`0.61–1.43 ms`**. Combined window-thread CPU time per frame (`pump + draw`) is **`0.62–1.46 ms` (`< 9%` of a 60 Hz budget)**.
   - In `wheel-pan-zoom` (`N = 14`), `uploads = 1680 drawn / 14 uploaded / 336 rows / 14 writes`: after uploading the 14 `80×24` grids once on frame `#0`, 119 continuous pan/zoom frames issue **`0` cell buffer writes** (`draw p50 = 0.610 ms`, `p95 = 1.189 ms`), proving camera movement is purely vertex/Slug-shader bound and VSync-limited.
   - In `fullscreen-tui` (`N = 1`), rewriting all 24 coloured rows on alternate screen (`2,538 rows` uploaded across `111` updates in `120` frames) costs only **`0.628 ms` `draw p50`** (`1.519 ms` `p95`), sustaining **`52.60 FPS`**.

2. **`cat-src` (`N = 14`, `28.81 FPS`) and `seq` (`N = 14`, `36.81 FPS`) → Limited by (a) Host CPU Oversubscription (`load ~22` + `14` PTYs + `14` VT workers + `termd` on 8 cores) and (b) Per-Terminal `queue.write_buffer` + Cell Packing at `N = 14`**:
   - **Evidence**:
     1. **Core oversubscription**: Each active flood terminal runs a producer (`cat`/`seq`), `g3d-hold`, `g3d-termd`'s `libghostty-vt` parser, and a `term-session` `glyph-vt` worker thread. At `N = 14` on top of host `load = 22.4` (`~50+` runnable threads on an 8-core M2), the window thread suffers scheduler preemption mid-frame (`draw p50 = 2.355 ms`, `p95 = 36.312 ms`; `seq N=14` frame `#16` `rnd = 82.2 ms` vs `p50 = 1.635 ms`). Confirming this: when host load was `58.5`, `cat-src N=14` fell to `5.63 FPS`; dropping load to `22.4` quintupled it to `28.81 FPS` with no renderer change.
     2. **Per-frame GPU upload fan-out + frame-`#0` submit**: Across `121` frames, `cat-src N=14` uploaded **`750` terminal snapshots (`17,915` rows, `826` `queue.write_buffer` calls ≈ `6.8` `write_buffer` calls/frame)** and spent `102.1 ms` in frame `#0` `submit` (`134.6 ms` total). Steady-state CPU `draw p50` (`2.355 ms` for 14 terminals = `~168 µs/terminal`) has `7×` headroom inside 16.6 ms once unloaded.

3. **`yes` Total Process CPU (`1.72 s` at `N = 1`, `3.98 s` at `N = 14` over `2.3–3.0 s` wall) → Background `term-session` `Vt::feed` Scroll Parsing (`~97 ns/line`), Completely Isolated from the Window Thread**:
   - **Evidence**: Window-thread `pump sum` is **`1.68 ms`** total over `2.96 s` (`0.057%`), and `uploads` is just **`20` snapshots (`342` rows)** across `1,680` drawn terminal-frames because `Vt::fill` detects that scrolling `"y"` over `"y"` leaves cells unchanged. Practically all of `Proc CPU` (`3,982 ms` across 14 worker threads = `~96 ms/s` per worker thread) is spent in background `TerminalSession` threads draining `yes` (`"y\r\n"`) at `termd`'s PTY delivery rate without touching frame rate (`40.52 FPS`).

4. **Single-Frame Tail Spikes (`48–135 ms`, and the `582 ms` Spike Reported Earlier) → `CAMetalLayer::nextDrawable` (`acq`) Swapchain Stall + Cold Frame-`#0` Metal `submit`**:
   - **Evidence**: In 10 of 12 cases, `worst_ms` is `90–99%` inside `acq` (`g.surface.get_current_texture()`), e.g. `mixed-8yes-1cat-1quiet` frame `#4`: `total = 98.487 ms` = **`acq 95.888 ms` + `render 0.695 ms` + `submit 1.893 ms` + `pump 0.011 ms`**. Earlier inline probes measured `now.elapsed()` across `get_current_texture()` + `present()`, attributing macOS WindowServer/compositor drawable stalls (`CAMetalLayer::nextDrawable`) to `draw_ms`.

## 5. Far End of Scale (`N = 50, 100, 200` Idle `80×24` Terminals — Baseline & Limiter Audit)

Measured with `./tools/wall-perf.sh --modes scale` on `workstation` (NVIDIA RTX 5090, Wayland `1920×1080@74.97 Hz`, `scale_factor = 1.0`, merged `wall` `f5f5c35`, `WallCamera::MIN_ZOOM` aligned to `wall_core::camera::ZOOM_MIN = 0.05` so renderer and rules agree down to `0.05 px/wu`). Each `80×24` terminal is populated with 24 ANSI-coloured lines and idles under `--shell-ttl`.

### A. Daemon & OS Limits

- **`g3d-termd` compiled cap**: `max_terminals = 8,192` (`g3d-termd/src/main.rs:152`).
- **Linux (`workstation`)**: Default soft `RLIMIT_NOFILE = 2,048` (`hard = 2,097,152`) and `/proc/sys/kernel/pty/max = 4,096` — all `N = 50, 100, 200` start and adopt cleanly without raising limits.
- **macOS (`laptop-2`)**: Default login-shell soft `RLIMIT_NOFILE = 256` (`hard = unlimited`) and system-wide `kern.tty.ptmx_max = 511`. Because `g3d-termd` does not raise its own `RLIMIT_NOFILE` at startup (`holder` and `brain` each hold 1 master PTY fd + history blob fds per terminal), an un-tuned macOS shell hits `EMFILE` (`Too many open files`) before `N = 200` unless soft `ulimit -n` is raised (supported via `--scale-nofile 4096`), and hits the kernel PTY ceiling near `511` minus other live PTYs on the host. (All `N` `term-session` instances in `glyph3d-native` multiplex over **one** Unix socket in `SessionHub`, so the window process itself uses `O(1)` sockets.)

### C. Scale Limiter Answers & Evidence

1. **Startup, Adopt, and Memory Scale Smoothly (`~0.16 ms/terminal` adopt, `~238 KiB/terminal` window RSS, `~115 KiB/terminal` daemon RSS)**:
   - Adopting `200` live terminals on `PendingTermd`'s background thread takes **`32.0 ms`** (`229.1 ms` from process start to `first_terminal_frame_presented`, with paper already on screen before adopt finishes).
   - Going from `50` to `200` populated `80×24` terminals (`+150` terminals = `+288,000` live cells) adds only **`+34.8 MiB`** to `glyph3d-native` (`208.3 → 243.1 MiB`) and **`+16.8 MiB`** to `g3d-hold` + `g3d-termd` (`21.7 → 38.5 MiB`).

2. **View Culling Today — NONE (`200.0 drawn/f` and `2.923 ms` CPU draw even when 199 of 200 terminals are off-screen)**:
   - **Does `WallRenderer` upload or draw off-screen terminals?** Unchanged screens do **not** re-upload cell rows (`terminals_uploaded = 0` during pan/zoom), **but** `WallRenderer::prepare` (`native/src/wall/renderer.rs`) unconditionally calls `queue.write_buffer(&gpu.uniform_buf, ...)` (`64 B`) for every terminal in `frame.terminals` every frame, and `record_into_pass` records `3–5` draw calls (`panel_pipeline`, `fill_pipeline` `0..1920`, `ink_pipeline` `0..1920`, `cursor_pipeline`) for every off-screen terminal.
   - **Does `describe.rs` build chrome for off-screen terminals?** Yes: `describe_frame_chrome_with_scrollback` (`native/src/wall/describe.rs`) builds `TitleBarDesc` (shaping Slug `LabelGlyphGpu` quads), `GroupFrameDesc`, `ScrollbackIndicatorDesc`, and `SelectionOutlineDesc` for all `N` terminals regardless of `camera.visible_world_rect(viewport)`. Only `WallNames` (`crates/wall-core/src/names.rs:598-605`) culls `map_labels` to on-screen boxes.
   - **Measured proof**: At `N = 200`, framing `t01` alone (`wall.reveal t01`, leaving `199` terminals off-screen) still reports **`200.0 drawn/f`** and **`draw p50 = 2.923 ms` (`p95 = 5.693 ms`)** — statistically identical to `Fit-All` (`2.934 ms` `p50`).

3. **Far-Zoom LOD Cut-Over Today — Map Labels Cut Over, Cell Pass Still Runs Underneath (`384,000` sub-pixel cell quads at `~4.6 px` terminal height)**:
   - **Is there an LOD cut-over like the JS wall?** `WallNames` (`crates/wall-core/src/names.rs`) implements the JS title-bar → map-label cut-over (`MAP_LABEL_ON_PX = 140.0` CSS px width / `MIN_TEXT_PX = 8.0` CSS px text height), **and the cell pass (`fill_pipeline` + `ink_pipeline` + `cursor_pipeline`) still runs underneath it** at every zoom!
   - By contrast, in JS (`packages/glyph3d-core/src/collections/GlyphFarLod.js`), `GlyphFarLod` (`showGlyphsPx = 1.0` CSS px per row, matching `[lod] show_glyphs_px = 1.0` in `config/defaults.toml`) disables `VIEW_LAYER` on any terminal whose row height on screen is `< 1.0` CSS px, skipping both the cell fill pass and the Slug ink pass while keeping the panel (`PanelBatch`) + 1 far-tint quad + map label.
   - **Measured proof**: At `zoom = 0.08` CSS px/wu (each `80×24` terminal is `57.6 × 0.08 = 4.6` CSS px tall = `0.19` CSS px/row), `WallRenderer` still submits all `200 × 1,920 = 384,000` cell fill and Slug ink instances on top of 200 map labels, pushing `N = 100` `draw p50` up from `1.012 ms` → **`1.332 ms`** and `N = 200` `draw p50/p95/max` to **`3.056 / 6.057 / 8.333 ms`**.

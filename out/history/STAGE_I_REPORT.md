- **Call-site sweep** (the only API breakage that touched us — 0.33.2

  zero-warning discipline forbids deprecation warnings, so all 5 sites
  moved):
  - `Mat4::look_at_rh` → `glam::camera::rh::view::look_at_mat4`
    (scene.rs demo camera; glyph_scene.rs Front/Orbit cameras)
  - `Mat4::look_to_rh` → `glam::camera::rh::view::look_to_mat4`
    (glyph_scene.rs Fly camera — the pick-fix path; direction-based,
    no eye−target cancellation, semantics preserved exactly)

    (both files). The `directx` module is documented as "DirectX and
    WebGPU NDC convention: Z range [0, 1], Y-up" — exactly the convention
    `Mat4::perspective_rh` always used, and the one wgpu requires.
    (`opengl` is z [−1,1]; `vulkan` is y-down — both wrong for wgpu.)

## Divergence analysis

**None.** All four views are byte-identical between glam 0.30.10 and
0.33.6. No re-baseline was performed; `out/tooling-ab/baseline/` still
holds the Part-1 renders.

Why byte-identity is plausible (not luck), confirmed against the
published 0.33.6 sources in the local registry:

- The deprecated type methods in 0.33.6 retain their original bodies
  (e.g. `Mat4::perspective_rh`'s `sin_cos`-based formula is character-
  for-character the 0.30 formula), and the new `camera` free functions
  share the same `camera_impl` implementation the methods now delegate
  to — the "should be the same math" hedge from fence 2's reasoning is,
  for these five functions, "is the same math."
- glam's per-version bit-for-bit determinism guarantee held across this
  version boundary for every path we exercise: view-proj construction
  (the only f32 CPU-side camera math that reaches the GPU), the f64
  analytic pick ray (DVec3 cross/normalize/dot — stage-G oracle picks
  all PASS, so cross-version f64 vector ops agree to the bit on the
  asserted paths), and the Gribb-Hartmann frustum extraction.
- One reviewed candidate for ULP drift did NOT trigger: 0.33.4
  "replace scalar `recip()` calls with explicit division in vector
  implementations." Our renders are byte-identical regardless — either
  the aarch64/NEON path already used explicit division, or the affected
  ops agree bitwise for all values this renderer produces. Noted so a
  future platform (SSE2/x86) re-baseline has a first suspect if a diff
  ever appears there.

# Glyph Engine Testing & Verification Guide

Root `AGENTS.md` is canonical for what each check compares and cannot see;
this is the working procedure. Counts (tests, gates, mutations) are printed
by the tool on every run and deliberately not repeated here: a number in
prose is a number that rots (this file said "222 tests" long after it was
false).

## 1. The tool, by intent

| Intent | Command | What it does |
| :--- | :--- | :--- |
| Iterate | `cargo glyph test <scope>` | Brings the renderer up to date, then runs the gates for a scope: `rust` (build, no-UI check, clippy, doc, tests: no pixels), `render` (anything that moves a pixel: pixel-ab, picks, layout oracles), `corpus` (fixtures, generators, vendored inputs). The verdict line says how many gates ran. |
| Land | `cargo glyph test` | All gates. Red on any warning, failed test, test count under `test_floor`, or golden mismatch. |
| Validate a commit | `cargo glyph test --frozen` | Asserts the renderer is already current instead of building it; staleness IS the finding. |
| One check | `cargo glyph gate <name>` | A single gate by name (`cargo glyph gates` lists them, with what each cannot see). |
| Prove the checks | `cargo glyph prove [--changed \| --mutation <name>]` | Applies declared mutations; each must redden its gate for its stated reason. Reports coverage. `--changed` proves the mutations whose target file differs from HEAD. |
| Run | `cargo glyph run [args]` | Builds if stale, then runs the renderer in YOUR directory; no arguments opens the launcher. |

Do not hand-run `cargo build`, `tools/*.sh` or the binary's check flags in
place of a gate: the ordering between them is what the tool holds for you.
`cargo nextest run --workspace` (`just test`) is fine for a fast manual loop;
the gate is `cargo glyph test`.

`test rust` is NOT the golden check: pixels are `cargo glyph test render`
(or `cargo glyph gate pixel-ab`). Golden PNGs are never regenerated by the
tool; re-baselining is a human act (root `AGENTS.md` § pixel-ab).

## 2. Checks worth knowing by name

- `pick-oracle`: scripted picks and pixel-ray round trips against an
  independent Python fold oracle (`alpha.rs`, `wide.txt`, `sub/deep.py`,
  `long.md`, `text.rs`, `emoji-view.txt`).
- `hyper-oracle`: HyperLayout, the production engine, held to the
  oracle-backed fold bit-for-bit (records, host and device Pass 2 in both
  slot formats, paint, and the visible kernel against Pass 2) over the
  fixture corpus, `g-pick-repo`, `g-cluster-repo` and the chunk-cut fixtures.
- `pixel-ab`: the golden views byte-compared per rasterizer key, plain and
  under each `golden_equivalents` entry (`--field-mode derived`,
  `--field-mode visible`; five syntax views are exempt from the visible one,
  by name, and their distance is still printed).

## 3. Performance

```sh
# Amortized: 1 cold + 4 warm runs. GLYPH_FLAGSHIP_REPO names a large repo
# (bench_hyper.py defaults --repo to it, else this repo).
python3 tools/bench_hyper.py --repo "$GLYPH_FLAGSHIP_REPO" -n 5 --field-mode derived --color-mode flat
```

It reports walk, Pass 1, Pass 2, backend total (MB/s) and visual init. For
one run with the stats line, `cargo glyph run --load-repo <dir> --frames 1`.
Report interleaved A/B runs with machine load noted; the M2 is fanless and
needs cool-downs. Visible mode's GPU timings: `GLYPH_VISIBLE_TIMING=1` (per
frame, offscreen) or the F8 HUD.

## 4. Launcher vs in-app UI

- **Launcher** (`cargo glyph run` with no arguments, `cargo glyph tui`, or
  `glyph3d-native --launcher`): a terminal front end of the renderer
  (`native/src/launcher/`, default feature `launcher`). Its state is a
  `LaunchConfig`; choice rows are the flags' clap `ValueEnum` variants.
  Enter saves what you changed into `launch_config.toml` (in place, comments
  kept), writes the launch to a temp file and runs the same binary on it
  with `--launch-config`; the menu returns when the window closes.
- **In-app UI (egui)**: F1 Debug panel (field mode, LOD sliders, z spacing,
  selection), F7 agent sessions, F8 field HUD, F2 screenshot (with
  `GLYPH_POSE_PRINT=1` it prints the `--cam-pose` that reproduces the
  frame; the Debug panel's "copy pose" does the same).

## 5. Platforms

Hardware specifics (unified vs discrete staging, chunk sizing, copy
alignment, golden keys) live in `native/AGENTS.md` § "Apple Silicon vs.
Desktop": one copy. Golden sets exist for `metal-apple` and
`vulkan-nvidia`; a new host's key is red until a human adopts a set
(`cargo glyph drift` compares it against the others).

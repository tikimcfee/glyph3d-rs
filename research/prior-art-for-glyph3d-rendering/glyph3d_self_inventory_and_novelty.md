## Q1. What glyph3d (the Rust renderer, glyph3d-native) actually does: its distinctive mechanisms, technically stated

### Takeaway
glyph3d-native is a pure-Rust wgpu renderer. It lays out real source text (one file, an agent transcript, or a whole repo of up to ~100 M glyphs) as a 3D field of monospace glyphs and draws them with Slug-style analytic Bézier coverage. Three things set it apart: (a) its production CPU layout (HyperLayout) is held bit-for-bit to an oracle-backed serial fold and a segmented monoid scan, both ported from and checked against a recorded JS corpus; (b) a "visible" field mode keeps the source bytes, a line table and the atlas trie resident on the GPU, and each frame lays out only the visible lines in a compute kernel (one serial walk per line segment, emoji ZWJ sequences included) that is bit-equal to the CPU engine; (c) a declared, mutation-proved verification battery with per-rasterizer golden pixel sets.

### Cited Findings

**Overall framing**
- Self-description: "A renderer that lays source code out as text in 3D and draws it on the GPU: a single file, an agent transcript, or an entire repository as a field of files you fly through. Glyphs are drawn with Slug-style analytic coverage (resolution-independent curves, no glyph textures), in pure Rust on wgpu." It claims "SCALE with exactness". The layout engine is "held bit-for-bit to an independent reference", and every offscreen frame is "byte-deterministic". Platforms are Metal (Apple Silicon) and Vulkan (Linux x86_64). — [R/README.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/README.md) (lines 1–19)

**1. Layout as a fold, a monoid scan, and a bake, held bit-exact to an oracle (the "reference port")**
- Serial fold (`native/src/fold.rs`), segmented monoid scan (`native/src/scan.rs`), checkpoint bake (`native/src/bake.rs`), all ported from vendored JS oracles (`engine/fixtures/inputs/glyphPipelineScan.js`, `glyphPipelineKernels.js`, `glyphBake.js`). — [R/native/src/scan.rs](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/native/src/scan.rs) (header lines 1–25)
- scan.rs header: "The serial fold in `fold.rs` is a left-to-right recurrence and a GPU cannot run one. Recasting it as an ASSOCIATIVE monoid is what makes it parallel, and the price is that associativity has to be true rather than assumed… Sweeping chunk and group sizes and getting identical integer lanes IS associativity checked in situ." The dispatch shape is `chunk_reduce -> spine_reduce -> spine_scan -> partial_scan -> apply -> resolve_x -> paginate -> bounds`. The precision contract is tiered: integer lanes are bit-equal, while f32 x-lanes are bit-equal or within 1e-4, because "regrouping an f32 chain changes its value". — [R/native/src/scan.rs](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/native/src/scan.rs)
- Tests pin the monoid's domain and its preconditions: `the_monoid_is_associative_on_every_integer_field` (scan.rs:779), `mixed_wrap_is_outside_the_monoid_s_domain` (:932), `mixed_mode_is_outside_the_monoid_s_domain` (:973). glyphBake.js: "because the fold is an associative monoid, the layout state at ANY [byte] … checkpoint". — [R/native/src/scan.rs](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/native/src/scan.rs); [R/engine/fixtures/inputs/glyphBake.js](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/engine/fixtures/inputs/glyphBake.js)
- Volumes cleared by the reference-port gate: 26 fixtures and 23,552 trie entries; serial fold of 155,222 leaders with 1,874,328 per-byte lanes bit-exact; 208 scan cases across 8 tunings, with 1,188,024 leader-lanes bit-exact and 53,752 within 1e-4; bake over 8 fixtures, 27,315 leaders, 167 checkpoints and 530 seed queries. — [R/AGENTS.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/AGENTS.md) ("reference-port" section)
- The author's own later verdict on the scan: it "is correct… and the kernels run at memory speed. But it is shaped for the wrong problem": it materialises 90 M slots (1.8 GB) when only a few hundred thousand are drawn, the hard parts (UTF-8, greedy emoji chain, syntax state, f32 running x) are "serial per line anyway", and "the natural parallel unit is the line". The GPU scan engine (CubeCL) was retired on 2026-10-09. — [R/out/GPU-DIRECTION-2026-10-09.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/GPU-DIRECTION-2026-10-09.md) (§2, lines 178–205)

**2. HyperLayout: CPU two-pass layout into unified-memory-mapped GPU buffers**
- `native/src/layout_hyper.rs`: "Direct-to-arena streaming layout with Rayon parallelism… Zero SoA 52 B/byte intermediate heap allocations… Cache-resident register evaluation of positions, wrap, and pagination." Pass 1 computes per-chunk slot bases; Pass 2 writes disjoint ranges without locks. — [R/native/src/layout_hyper.rs](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/native/src/layout_hyper.rs) (lines 1–8); [GPU-DIRECTION §2a](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/GPU-DIRECTION-2026-10-09.md)
- `layout_hyper/device_alloc.rs`: "Device buffer allocation and staging for unified and discrete memory architectures": `layout_device_unified` writes into mapped device memory on unified Metal; a mapped staging buffer plus one copy is used otherwise. — [R/native/src/layout_hyper/device_alloc.rs](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/native/src/layout_hyper/device_alloc.rs) (lines 1–5, 114)
- Quoted figures on the glyph3d-js corpus (1,306 files, 97.0 MB, 95.2 M glyphs), Apple Silicon Metal: ~168 ms backend (576.9 MB/s) in flat colour and ~215 ms (450.9 MB/s) with syntax colour. AGENTS.md: "These figures are from late 2026-09… they have not been re-measured since." On Linux (RTX 5090, 93 MB crates.io tree, 90.2 M glyphs), the stored modes measured ~460 ms, "85 % data movement of a 1.8 GB slot stream", and 204 ms with host-memory staging. — [R/AGENTS.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/AGENTS.md) ("Performance characteristics"); [GPU-DIRECTION](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/GPU-DIRECTION-2026-10-09.md) (lines 10–25)
- Intra-line chunk cuts (C15): a line longer than the 64 KiB chunk threshold is cut inside the line. A cut lands only before an ASCII byte, because the atlas asserts that no sequence has an ASCII member after its first. The continuation is seeded with the running f32 sum. — [R/AGENTS.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/AGENTS.md) ("Intra-line chunk cuts")

**3. Three field modes behind one `GlyphField` trait (crates/)**
- `instanced`: a 32 B record per glyph. `derived`: a 20 B record, with the vertex stage deriving Y/Z from per-file tables. `visible`: nothing per glyph; the source bytes and line table stay resident, and each frame the GPU culls to the lines in view and lays out only those. "All three render the same pixels on every golden view", except that visible mode applies no load-time syntax colour by design. — [R/README.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/README.md) ("Field modes"); crates `glyph-field`, `glyph-field-instanced`, `glyph-field-derived`, `glyph-field-visible` — [R/AGENTS.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/AGENTS.md) (Layout)

**4. Visible mode: GPU-resident bytes, line table and trie, with per-frame compute layout**
- Line table (M1): Pass 1 emits a 16 B `LineEntry {byte_start, item, base_row, glyph_count}` per line, plus a 24 B `SegmentSeed {line, byte_offset, col, seg_adv, cells}` at a cut every 2048 bytes (before an ASCII byte only). On a 93 MB tree that is 2,660,879 lines and a 42.6 MB table built in 72 ms on 32 threads. — [R/out/VISIBLE-MODE.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/VISIBLE-MODE.md) (M1, lines 9–55)
- Exact x without f64: "every trie advance is 0, 1 or 2 cells" (asserted over all 0x110000 codepoints), so `f32(cells) × cell_adv` reproduces the fold's f64 sum narrowed to f32. — [R/out/VISIBLE-MODE.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/VISIBLE-MODE.md); [GPU-DIRECTION §Round 2.3](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/GPU-DIRECTION-2026-10-09.md)
- The kernel, `crates/glyph-field-visible/shaders/visible_layout.wgsl`, runs "one invocation per SEGMENT (a whole short line, or one cut of a long line), a serial walk over its bytes that resolves every leader through the resident atlas trie — in cluster mode exactly as HyperLayout's `char_resolve.rs`… and writes the Derived slot (20 B)… with the bits HyperLayout's device Pass 2 writes." Culling is `visible_cull.wgsl`: a per-file box test, a one-workgroup prefix, a per-line box test dispatched indirectly, then indirect layout and indirect draw, with "no readback on the frame path". Slot order is set by atomics. — [R/crates/glyph-field-visible/shaders/visible_layout.wgsl](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/crates/glyph-field-visible/shaders/visible_layout.wgsl) (header); [GPU-DIRECTION Round 2 §5](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/GPU-DIRECTION-2026-10-09.md)
- Measured on the 93 MB tree: backend 11–22 ms where the stored modes wrote 1.8 GB in ~460 ms; offscreen frames of the default view take ~0.7 ms. Resident cost is ≈1.5 B per source byte, against 19.4–31 B for the stored modes. — [R/out/VISIBLE-MODE.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/VISIBLE-MODE.md) (M2); [GPU-DIRECTION §3](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/GPU-DIRECTION-2026-10-09.md)
- Witness: hyper-oracle's sixth tier runs the GPU kernel headless over every line of every corpus and compares its `DerivedSlot`s byte-for-byte with the CPU device Pass 2. The prototype `jit-text` passed 44 of 44 on both RTX 5090/Vulkan and M2/Metal, which is "the property the pixel gates could never claim across vendors, held here at the slot level". — [R/out/VISIBLE-MODE.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/VISIBLE-MODE.md); [GPU-DIRECTION Round 2 §3](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/GPU-DIRECTION-2026-10-09.md)
- Per-glyph edits with no per-glyph storage (M3): selection, recolour, group, transform and so on are re-keyed by (item, byte) through a sparse override map. Selection lays the byte range out again into a mask buffer. — [R/out/VISIBLE-MODE.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/VISIBLE-MODE.md) (M3)

**5. Per-line wash LOD (greeking tiers)**
- `visible_wash.wgsl` is the wash tier: "one BOX per line whose rows project under `lod_glyph_px`, in its spans' mean colour… The box is the volume the line's glyphs would fill… z from segment 0's depth to the last segment's", with a 1 px fade band. Below a further threshold, files become one backdrop rectangle. — [R/crates/glyph-field-visible/shaders/visible_wash.wgsl](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/crates/glyph-field-visible/shaders/visible_wash.wgsl) (lines 1–24); [R/README.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/README.md)

**6. Slug-style analytic glyph curves in WGSL**
- `glyph_field.wgsl:247`: "Direct port of computeCoverage in GlyphField.js (Dobbie/Lengyel 'Slug'), including the stable-root fix and the near-horizontal line guard." It computes analytic coverage of quadratic Béziers for a +X ray, with fractional crossings. The atlas is prebaked (`assets/atlas/{curves,glyphmap,glyphs,codepoints}.bin`; 82,239 curves, 2.5 MiB) with a Noto colour-emoji sheet. — [R/crates/glyph-field-instanced/shaders/glyph_field.wgsl](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/crates/glyph-field-instanced/shaders/glyph_field.wgsl) (lines 244–250); [GPU-DIRECTION Round 2 §3](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/GPU-DIRECTION-2026-10-09.md)

**7. "back" wrap mode: wrapping costs depth**
- `--wrap-mode back` is the default: "a wrap costs DEPTH". A wrapped segment recedes in z rather than taking a new row. fold.rs: "A WrapBack line occupies exactly the row it sits on" (:428); "`wrap_segment` is the DEPTH… contributes to the ROW, which WrapBack makes zero" (:719). Only `repo-back-oblique` can see the z-order this creates. — [R/native/src/fold.rs](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/native/src/fold.rs); [R/AGENTS.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/AGENTS.md) ("Which view covers what")
- Related 3D paging: `fold::paginate` turns rows and columns into pages fanned in depth (`depth_per_col`, `x_page`, `y_page`), shared in `layout_hyper/page.rs`. — [R/AGENTS.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/AGENTS.md) (hyper-oracle C14)

**8. Emoji cluster sequence pass**
- Greedy longest-prefix sequence resolution: ZWJ families, flags, skin tones, keycaps and tag flags, with ≤9-codepoint lookahead. FE0F is dropped from the key, the head takes 2 cells and trailers take 0. The UCD-derived class table is `assets/atlas/cluster-classes.bin` and the trie has 4,166 sequences. On the CPU it is `layout_hyper/char_resolve.rs`; the same logic is ported into the GPU kernel. — [R/AGENTS.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/AGENTS.md) (Fences, hyper-oracle); [visible_layout.wgsl header](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/crates/glyph-field-visible/shaders/visible_layout.wgsl); [GPU-DIRECTION Round 2 §3](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/out/GPU-DIRECTION-2026-10-09.md)

**9. Picking via an analytic pixel ray**
- `glyph_scene.rs` header: "PICKING IS CPU-SIDE, deliberately: every glyph's geometry is derivable deterministically (a picked file's records are re-produced by re-running…)… ~1.3k ray-AABB tests cost microseconds… screen px → ray (ANALYTIC, f64…)". The pick-oracle gate holds pixel-ray round trips to an independent Python fold oracle. By contrast, glyph3d-js used a GPU multi-channel ID render pass. — [R/native/src/glyph_scene.rs](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/native/src/glyph_scene.rs) (lines 4–18); [J/README.md](file:///home/ivan/dev/glyph3d-js/README.md) ("GPU picking")

**10. Agent-transcript browsing**
- `native/src/agent_transcript/` has adapters for Claude Code JSONL (2-pass tool pairing), Antigravity, and Kimi `wire.jsonl`, normalised to `AgentSession`/`AgentTurn`/`ToolCallRecord`/`FileActionRecord`. The F7 key opens the session browser, and `crates/glyph-session-dirs` holds the table of session locations. — [R/native/src/agent_transcript.rs](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/native/src/agent_transcript.rs) (lines 1–8)

**11. The verification battery**
- 15 gates and 61 mutations are declared in `build.toml` (counted 2026-10-10), plus 10 golden views in two per-rasterizer sets (`metal-apple`, `vulkan-nvidia`). `glyph/src/prove.rs`: "break each check, require it to notice… green first… assert applied… builds first… right gate/text… restore proven… Reported as COVERAGE, not a pass count." — [R/glyph/src/prove.rs](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/glyph/src/prove.rs) (lines 1–25); [R/build.toml](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/build.toml)
- Golden PNGs are class "golden": the tool refuses to regenerate them, and re-baselining is a human act. The key is `<backend>-<vendor>` from the live adapter, and `ADAPTER.txt` records the driver. `drift` is an instrument (isolated edge flips vs clustered), not a gate. `golden_equivalents` re-renders every golden under `--field-mode derived` and `--field-mode visible` and requires byte equality with the same PNG, with named, priced exemptions. — [R/AGENTS.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/AGENTS.md) ("pixel-ab", "Golden equivalents")
- "A check must refuse to pass having compared nothing", and a test floor works as a ratchet. Every gate's `blind_to` is documented. — [R/AGENTS.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/AGENTS.md)

### Inferences
- The most technically distinctive pieces are internal to the layout and verification pipeline: GPU per-segment layout from resident bytes, held bit-equal to a CPU engine and, transitively, to a JS oracle, across two GPU vendors. The visual premise (code as 3D text) is less distinctive.
- A precise external search should treat "Slug in WGSL" and "GPU instancing of glyphs" as known building blocks, not as claims.

### Gaps
- The 577 MB/s figure has not been re-measured since late September 2026 (the repo says so), and visible-mode load figures exist only for one Linux box and the M2.
- No glyph3d-native page is published on ivanlugo.dev. The projects page lists only the JS project (see Q2).

## Q2. Prior art the author has already identified (website and repos), and what was said about each

### Takeaway
The published survey at ivanlugo.dev/prior-art/ (six volumes, compiled May 2026, explicitly "assembled by Claude") covers code-visualization prior art thoroughly: rendered-text tools, code cities, VR IDEs and commercial maps, web toys, and GPU text. Its positioning claim is about the JS project's five-part "slot", not any rendering mechanism. The repos add a GPU-text teardown and a game-engine survey (glyph3d-js `docs/perf-swarm/`). In the Rust repo, the author's sharpest prior-art statement is "Nobody ships this" about per-line GPU layout from bytes.

### Cited Findings

**Site framing and positioning (Volume 06)**
- The site splits the field into a large "metaphor" branch and a small "actual source text as spatial primitive" branch: "roughly six research prototypes in fifteen years", almost none open-sourced, "none are GPU-instanced at repo scale". The closest published 3D precedent named is Code Park. The page also says it was compiled May 2026 and assembled by Claude. — [ivanlugo.dev/prior-art/](https://ivanlugo.dev/prior-art/)
- The five-requirement slot is: real source text as the primitive, a whole repo at once, GPU instancing in one draw call, in-browser with no headset, and maintained/openable today. "Dropping any one requirement lets an existing tool fill the slot." Prior occupants and their fates: Code Park (never open-sourced), Code Canvas (never released), CodeHouse (never released), Primitive (rendered architecture, ran out of funding), VRIDE (dormant since 2021, not repo-scale), Codemap/pfff (2D, went quiet). "None of these failed on the merits of the idea." Anchoring citations: Code Thumbnails 2006, Code Bubbles 2010, Code Canvas 2010, Code Park 2017, Dominic et al. 2020/2022, CodeCity 2008, SeeSoft 1992, Limberger et al. Web3D 2024, and Lengyel i3D 2018 (patent public-domain March 2026). — [ivanlugo.dev/prior-art/positioning/](https://ivanlugo.dev/prior-art/positioning/)
- The site's projects page lists only glyph3d-js ("GPU-instanced 3D text rendering for Three.js… thousands of glyphs in a single draw call") and links glyph3d.dev and github.com/tikimcfee/glyph3d-js. It does not mention the Rust renderer. — [ivanlugo.dev/projects/](https://ivanlugo.dev/projects/)

**Volume 01, rendered-text lineage (what the author said)**
- SeeSoft (Eick, Steffen, Sumner, Bell Labs 1992): each line is a coloured pixel-row with a reading window; the historical root; 2D.
- Code Thumbnails (DeLine et al., MSR, VL/HCC 2006): programmers remember files spatially; influenced minimaps.
- Code Canvas (DeLine & Rowan, MSR, ICSE NIER 2010): infinite pan/zoom canvas with semantic zoom; never released; it became Debugger Canvas (retired) and VS Code Map.
- Code Bubbles (Bragdon, Reiss, Zeleznik et al., Brown, CHI/ICSE 2010): the canonical citation for spatially arranged editable fragments.
- Codemap/pfff (Padioleau, Facebook ~2010–2016): a zoomable treemap showing real highlighted source at high zoom; "nearest 2D ancestor in fidelity at scale"; dormant.
- Haystack Editor (YC S24, 2024): VS Code fork with code cards on an infinite canvas; closed.
- CodeRibbon (~2021): files tiled into a horizontal ribbon.
- Code Park (Khaloo, Maghoumi, Taranta, Bettner, LaViola, UCF, VISSOFT 2017): class-as-room with highlighted source on the walls; never open-sourced; "closest 2017 Unity ancestor to glyph3d's premise".
- CodeHouse (Hori, Kawakami, Ichii, Hitachi, VISSOFT 2019): rooms of real source in a virtual cylinder; unreleased.
- IDEvelopAR (Trier, VISSOFT 2022): HoloLens code panels; not released.
- VR-Native Live Programming (Geier et al., HPI, PAINT 2022): Smalltalk AST in VR.
- VRIDE (U. Chile, Bergel/Genovese, SCCC 2021): open Unity project, code on cube faces; "closest open, runnable, 3D, real-text environment".
- code-vr (NUI Lab, Colorado State): Rust/Vulkan/OpenVR/LSP; perpetually under construction.
- Primrose (McBeth, 2014–): editor rendered to canvas and textured onto 3D in WebVR; "closest technical sibling", but a canvas blit, not instanced per-glyph quads, and a single editor, not repo-scale.
- RiftSketch (Peiris 2014).
- CodeSparks (Moseler & Diehl, SCP 2023): in-code glyph overlays; closest 2D analogue to glyph3d's highlight layer.
- Empirical studies: Dominic et al. ICPC 2020/EMSE 2022 (VR comprehension accuracy held, higher cognitive load); Rzayev et al. CHI 2021 (reading in HMDs is slower); CodeCity VR vs screen (VISSOFT 2021/IST 2022).
- Dynamicland (Victor et al.): "the philosophical extreme". — [ivanlugo.dev/prior-art/rendered-text/](https://ivanlugo.dev/prior-art/rendered-text/)

## Q3. Candidate novel elements and targeted web checks (queries, hits and null results)

### Takeaway
No direct precedent was found for: (1) per-frame GPU layout of only the visible lines from resident source bytes, held bit-exact to a CPU engine; (2) wrap-into-depth; (3) emoji ZWJ sequence resolution inside a GPU layout kernel; (4) repo-scale (~10^8 glyphs) real-text 3D rendering with exact layout. Precedents exist for the building blocks: monoid scans over text positions (Zed SumTree, xi ropes, Vello's GPU monoids), greeking (InDesign, Illustrator, HOOPS), GPU-resident character data (Zutty), Slug in WGSL (slug-webgpu, HarfBuzz 14 hb-gpu), semantic zoom of code (Code Canvas patent, ExplorViz 2025), and 3D replay of agent sessions over a repo map (Mindwalk, July 2026, buildings not text). Novelty is most defensible in the combination and the exactness discipline.

### Cited Findings

**Candidate A: visible-set GPU compute layout from resident source bytes (per frame, one serial walk per line segment, seeded long-line cuts, emitting draw records for analytic text)**
- Queries: "GPU compute shader text layout line breaking visible lines only"; HN Algolia "GPU text layout compute shader" (stories); "\"text layout\" GPU parallel paper line breaking massively parallel glyph positioning"; HN-targeted "GPU text layout compute shader shaping on GPU".
- Results: no GPU line-layout system found. Ragged Blocks (arXiv 2507.06460) is CPU structured-text layout. — [arXiv 2507.06460](https://arxiv.org/pdf/2507.06460)
- HN Algolia returned 0 story hits for "GPU text layout compute shader". — [HN Algolia API](https://hn.algolia.com/api/v1/search?query=GPU%20text%20layout%20compute%20shader&tags=story&hitsPerPage=20)
- The common Rust GPU text libraries (wgpu_glyph/glyph_brush, gfx_glyph) cache CPU-side positioning and break lines on the CPU, and Slug's layout is "handled in software". — [wgpu_glyph docs](https://docs.rs/wgpu_glyph); [gfx_glyph docs](https://docs.rs/gfx_glyph); [Slug paper PDF](https://www.sluglibrary.com/slug.pdf)
- The nearest precedent for GPU-resident character data drawn in compute is Zutty, a terminal emulator that renders "a fixed-width text grid entirely in graphics hardware" through OpenGL ES compute shaders. Its layout is a trivial cell grid, with no variable advances, wrapping, sequence resolution or 3D. — [Zutty (zutty-crt fork README)](https://github.com/jengelh/zutty-crt)
- HarfBuzz 14.0 (April 1 2026) added a GPU library that does Slug rasterization in the fragment shader (GLSL/WGSL/MSL/HLSL). Per the coverage, shaping and layout remain CPU-side. — [Phoronix, HarfBuzz 14.0](https://www.phoronix.com/news/HarfBuzz-14.0-Released) (search snippet; the page returned 403 on fetch); [hb-gpu.cc source](https://flutter.googlesource.com/third_party/harfbuzz/+/HEAD/src/hb-gpu.cc?autodive=0)
- The author's own survey of GPU-driven rendering (compute cull plus indirect draw, Haar & Aaltonen 2015, Nanite) supplies the culling half. That half is well-precedented. — [J/docs/perf-swarm/game-engine-techniques-survey.md](file:///home/ivan/dev/glyph3d-js/docs/perf-swarm/game-engine-techniques-survey.md)

**Candidate B: layout as a segmented monoid scan / prefix sum (row, col, x per byte), checked for associativity in situ**
- Queries: "parallel prefix sum monoid text layout line column GPU"; "Raph Levien parallel text layout GPU monoid"; "raphlinus stack monoid parallel parsing GPU scan blog"; "xi-editor rope monoid metric line column summary Zed SumTree".
- Results: strong precedent for the principle. Zed's SumTree is a B+ tree whose nodes store a combined (monoidal) summary, which makes offset ↔ line/row mapping and UTF-8 ↔ UTF-16 row/column conversion O(log N). — [Simon Willison on "Zed Decoded: Rope & SumTree"](https://simonwillison.net/2024/Apr/28/zed-decoded-rope-sumtree); [Plushcap summary](https://www.plushcap.com/content/zed/blog/rope-sumtree)
- Vello computes GPU buffer offsets by parallel prefix sum over a path-tag monoid ("monoidal reduce plus pre-scan"). — [Skia VelloComputeSteps.h](https://skia.googlesource.com/skia/+/chrome/m152/src/gpu/graphite/compute/VelloComputeSteps.h); [GPU-friendly Stroke Expansion, arXiv 2405.00127](https://arxiv.org/pdf/2405.00127)
- Levien's "stack monoid" (Sept 5 2020) uses a scan to parallelise bracket matching for GPU parsing. It does not apply prefix sums to text layout. — [raphlinus.github.io stack monoid](https://raphlinus.github.io/gpu/2020/09/05/stack-monoid.html)
- An HN commenter traces the bicyclic-semigroup paren-matching approach to Bar-On and Vishkin (1985). — [hn.svelte.dev item](https://hn.svelte.dev/item/48678623)
- No source was found applying a monoid scan to per-byte text-layout lanes (row/col/x with wrap and pagination) on the GPU. Even so, "monoid summaries for text position" is clearly established, and glyph3d itself retired the scan in favour of per-line serial walks.

**Candidate C: per-line wash LOD (each sub-pixel line drawn as one box spanning the volume its glyphs would fill, in its spans' mean colour, then a file rectangle)**
- Queries: "\"greeking\" text rendering below threshold point size lines as bars"; "semantic zoom source code lines level of detail overview 3D software visualization 2025 ExplorViz".
- Results: greeking is long-standing. InDesign's "Greek Type Below" replaces small type with a dimmed bar. Illustrator showed text blocks as grey bars for speed (2002 book quote). HOOPS Visualize offers a greeking mode (nothing, a grid of lines, or a filled box) below a point threshold. — [Adobe InDesign help](https://helpx.adobe.com/lt/indesign/desktop/get-started/settings-and-preferences/adjust-text-display-quality.html); [Weblio quote](https://ejje.weblio.jp/content/greeking); [HOOPS HPS Text API](https://docs.techsoft3d.com/hps/latest/api_ref/cs/class_h_p_s_1_1_text.html)
- SeeSoft (1992) already drew each line as a coloured row (author's Volume 01).
- Code Canvas patent US 8,561,015 (Microsoft, Rowan & DeLine, priority 2009-06-15, listed "Expired - Fee Related") claims zooming through abstraction layers, with source shrinking and eventually "not shown". It does not describe line bars. — [Google Patents US8561015B2](https://patents.google.com/patent/US8561015B2/en)
- ExplorViz's semantic zoom (arXiv 2510.00003, SE 2026) works at package/class/method level, not code lines. — [arXiv 2510.00003](https://arxiv.org/pdf/2510.00003)
- Verdict: the line-as-bar idea is old (SeeSoft plus greeking). Making it a GPU LOD tier inside a 3D text field, with the box spanning the wrapped line's depth (C28), is a narrow implementation detail.

**Candidate D: "back" wrap mode (a wrapped segment recedes in z instead of taking a new row) and depth-fanned pagination**
- Query: "3D code visualization line wrap into depth z axis text wrapping".
- Result: the closest match is the USAA patent family "System and method for data visualization and modification in an immersive 3-D environment" (US 10,452,227; 10,860,170; 11,188,189; 11,662,878; priority 2016-03-31). It shows code text in an X-Y plane with relationship indicators along Z. The code "may wrap circumferentially 360 degrees… about the user" and "may be split along the 360 degrees into several pages of code". That is page-level curvature around the viewer, not per-line wrap into depth. — [Google Patents US10452227B1](https://patents.google.com/patent/US10452227B1/en); [USPTO PDF](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10452227)
- No precedent was found for per-line wrapping into depth. glyph3d-js's TerminalGrid already had "scrollback paged into depth", which is the author's own earlier art. — [J/README.md](file:///home/ivan/dev/glyph3d-js/README.md)

**Candidate E: emoji ZWJ / keycap / flag sequence resolution inside a GPU layout kernel, bit-equal to the CPU**
- Query: "emoji ZWJ sequence resolution GPU shader compute grapheme cluster".
- Result: null. Hits were glossaries and a Warp terminal bug where ZWJ sequences render as separate glyphs. — [Warp issue #8739](https://upd.dev/warpdotdev/warp/issues/8739)
- Inference: GPU-side grapheme/sequence resolution appears unpublished. A second null-checking query (e.g., "Unicode segmentation on GPU") was not run, so confidence is moderate.

**Candidate F: repo-scale (~10^8 glyph) 3D real-text field, Slug-style analytic coverage, pure Rust/wgpu**
- Queries: "render entire codebase source text 3D GPU instanced glyphs millions wgpu 2026"; HN Algolia "codebase in 3D source code" (stories); "Slug algorithm WGSL wgpu implementation sluggrs"; HN Algolia "Slug font rendering".
- Results: the search surfaced only glyph3d-js itself as a 3D source-text renderer. — [github.com/tikimcfee/glyph3d-js](https://github.com/tikimcfee/glyph3d-js)
- HN 3D-codebase posts are dependency graphs: CodeLayers (Feb 2026, 5 pts) and dep-tree (Jan 2024, 180 pts). — [HN Algolia API](https://hn.algolia.com/api/v1/search?query=codebase%20in%203D%20source%20code&tags=story&hitsPerPage=25); [codelayers.ai](https://codelayers.ai); [dep-tree](https://github.com/gabotechs/dep-tree)
- Slug in WGSL already exists: diffusionstudio/slug-webgpu ports the HLSL to WGSL, with CPU shaping and band organisation and GPU rendering. Also Sluggish, and Slughorn (MIT, HN July 8 2026). — [slug-webgpu mirror](https://bulgariahome.duckdns.org/diffusionstudio/slug-webgpu); [Sluggish](https://gittrend.io/repo/mightycow/Sluggish); [HN Algolia Slug](https://hn.algolia.com/api/v1/search?query=Slug%20font%20rendering&tags=story&hitsPerPage=15)
- Slug's patent US 10,373,352 was dedicated to the public domain on 2026-03-17, and MIT reference shaders were published at github.com/EricLengyel/Slug. Since 2017 the band split was removed and "dynamic dilation" was added. — [Terathon, "A Decade of Slug"](https://terathon.com/blog/decade-slug.html)
- glyph3d's shader cites "Dobbie/Lengyel 'Slug'" and is a port of the JS predecessor's coverage function. The analytic-coverage technique is therefore prior art, and the use at repo scale is the contribution.

**Candidate G: per-glyph editing with no per-glyph storage (overrides keyed by (file, byte); selection re-laid out into a mask buffer)**
- No dedicated search was run. Rope/SumTree-style byte-offset addressing (Zed) is the general precedent for keying by byte offset, as noted under Candidate B. Treat as plausible-but-unverified novelty in the GPU-transient-slot context.

**Candidate H: 3D browsing of AI agent session transcripts**
- Query: "visualize AI coding agent session transcripts 3D spatial browser Claude Code JSONL viewer".
- Result: precedent found. Mindwalk (cosmtrek/Ricko Yu, MIT, July 2026) is a Go binary with a React/Three.js frontend that replays Claude Code/Codex/pi sessions on a 3D city-style map of the repo. Files are buildings by LOC, and colour marks glance/read/edit. It does not render source text. — [Better Stack guide on Mindwalk](https://betterstack.com/community/guides/ai/mindwalk-ai-agent/); [github.com/cosmtrek/mindwalk](https://github.com/cosmtrek/mindwalk)
- 2D viewers: claude-transcript-viewer, llmly, Euphony. — [claude-transcript-viewer](https://awesome.ecosyste.ms/projects/github.com%2Fjordankzf%2Fclaude-transcript-viewer); [llmly](https://pypi.org/project/llmly/)
- Verdict: the 3D agent-session idea is not novel as of July 2026. Rendering the transcripts and touched files as real text in the same 3D field may still differ.

### Inferences
- Ranked by the likelihood of surviving a prior-art search, strongest first:
  1. Visible-line GPU layout from resident bytes, bit-exact to a CPU engine across vendors, including emoji sequences on the GPU (A+E).
  2. The exactness discipline: a JS oracle → Rust fold/scan → CPU production engine → GPU kernel chain, with byte-equality at every tier (see Q4).
  3. Wrap-into-depth (D).
  4. The combination at ~10^8 glyphs (F).
- Weakest: Slug in WGSL, instancing, greeking/wash LOD, monoid scan over text, 3D agent sessions. Each has a direct precedent.
- The author's "Nobody ships this" statement is consistent with every null result here. It rests on absence of evidence from a handful of queries, so it should be presented as "no precedent found".

## Q4. Verification methodology: prior art and how glyph3d compares

### Takeaway
Each ingredient has established prior art: mutation testing to "test the tests", multi-baseline golden images (Skia Gold), per-driver expectation files (Mesa CI), FLIP-thresholded per-backend image comparison (wgpu, Vello), and reference shapers as oracles (HarfBuzz for rustybuzz/Allsorts). glyph3d's combination is unusual: it mutates its own gates, declared in a manifest and requiring each gate to redden for a stated reason, and reports coverage of gates rather than a mutation score. Its golden sets are byte-exact per rasterizer key, never tool-regenerated, and it adds "golden equivalents" (alternate code paths must reproduce the same bytes). No search hit described mutating CI gates themselves.

### Cited Findings
- Mutation testing is the standard way to "test the tests": mutants are run against the suite, survivors reveal gaps, and the practice is often gated on a mutation score in CI and run incrementally on changed files. A patent exists for mutation testing within CI systems (US 12,072,790). — [Justia, US 12072790](https://patents.justia.com/patent/12072790); [Pinpoint guide](https://testwithpinpoint.com/blog/mutation-testing-guide); [Chalmers thesis on mutation testing in CI](https://odr.chalmers.se/handle/20.500.12380/305137)
- The search found no source on verifying that each CI check, as opposed to unit tests over product code, can fail. — same query, null on that framing.
- Skia Gold (Chromium GPU pixel tests) accepts multiple approved baselines per test, uses exact matching by default, offers optional inexact matching for noisy tests, and triages in an external service. — [Chromium "GPU Pixel Testing With Gold"](https://chromium.googlesource.com/chromium/src/+/91d16c2b01d59d12e02b4b4f0116ea028beb94de/docs/gpu/gpu_pixel_testing_with_gold.md)
- Mesa CI keeps per-driver `-fails.txt`, `-skips.txt` and `-flakes.txt` expectation files for deqp-runner. Unexpected failures are re-run to detect flakes. — [deqp-runner MR 81](https://gitlab.freedesktop.org/mesa/deqp-runner/-/merge_requests/81); [Mesa commit adding flakes filter](https://android.googlesource.com/platform/external/mesa3d/+/30da82c%5E%21/); [deqp-runner crate](https://rust-digger.code-maven.com/crates/deqp-runner)
- wgpu's test harness compares images with NVIDIA FLIP using `ComparisonType::Mean` or `Percentile {percentile, threshold}` (suggested thresholds 0.01–0.1). Vello uses `nv_flip` for CPU-vs-GPU comparison. — [wgpu_test ComparisonType](https://wgpu.rs/doc/wgpu_test/image/enum.ComparisonType.html); [Vello compare.rs](https://skia.googlesource.com/external/github.com/linebender/vello/+/ac91c19fb5dfa77ea8c6eff9129c7518bda05cd9/vello_tests/src/compare.rs)
- Dawn added per-call tolerances for Mac M1 and SwiftShader. A WebKit 2021 thread notes that tolerance may need to vary by GPU model/driver. luma.gl advises recording backend/adapter details. — [Dawn commit](https://dawn.googlesource.com/dawn/+/e9ad15ae7fc03178d2e3c2f6954c02f6b48beeea%5E%21/); [webkit-dev 2021](https://lists.webkit.org/pipermail/webkit-dev/2021-October/032033.html); [luma.gl test utils](https://luma.gl/docs/api-reference/test-utils)
- Oracle-backed testing of text engines: rustybuzz passes 2221 of 2252 HarfBuzz shaping tests, and Allsorts used HarfBuzz output as its test reference. HarfBuzz runs OSS-Fuzz shape fuzzers. No published differential fuzzer across shapers was found. — [rustybuzz docs](https://docs.rs/crate/rustybuzz/latest); [Allsorts docs](https://docs.rs/allsorts); [HarfBuzz fuzzer commit](https://flutter.googlesource.com/third_party/harfbuzz/+/e3af529e511ca492284cdd9f4584666b88a9e00f%5E)
- How glyph3d compares (from its docs):
  - Mutations target gates, and each declares the gate and failure text it must produce. The prover refuses on an already-red gate, asserts the edit applied, requires the mutant to compile, byte-restores, and rebuilds products the mutant fed. It reports "N gates, C covered, U uncovered" rather than a kill rate.
  - Golden sets are keyed `<backend>-<vendor>` with an `ADAPTER.txt`, byte-equal (no tolerance), and never regenerated by the tool. `drift` classifies cross-vendor differences as isolated edge flips or clustered.
  - Golden equivalents require alternate field modes to reproduce baseline bytes.
  - The JS oracle is kept in its original language on purpose, so that a port cannot share a fault with the thing it validates.
  - Sources: [R/glyph/src/prove.rs](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/glyph/src/prove.rs); [R/AGENTS.md](file:///home/ivan/dev/glyph3d-rs/.claude/worktrees/maintenance-and-things/AGENTS.md) ("Earning a green", "pixel-ab", "Which language a thing is written in")

### Inferences
- glyph3d's byte-exact golden policy is stricter than Skia Gold's multi-baseline and inexact options and wgpu's FLIP thresholds. It achieves this by segregating by rasterizer, much as Mesa segregates expectations by driver.
- Mutating the verification gates themselves, with coverage reported per gate, is the methodological element least represented in what was found. It is closest to classic mutation testing and to the TDD "see it fail" norm, applied one level up.
- The cross-vendor slot-level byte equality of the GPU kernel (Metal and Vulkan producing identical layout records) answers a known pain point in the per-vendor tolerance literature: numeric equality holds even where pixels cannot.

### Gaps
- WPT reftests were not fetched (no citation gathered), so they are not cited here. They are the canonical render-vs-reference precedent for layout engines and should be added if needed.
- Google's published mutation-testing-at-scale work (Petrović & Ivanković) and cargo-mutants were not fetched, so they are not cited.
- Mutation testing of test infrastructure or CI gates was searched once, with a null result on that framing. A Scholar search for "mutation analysis of test oracles" or "checked CI checks" was not possible with these tools.
